## High Priority (Address Soon)

**Silent error swallowing throughout catch blocks:**
- Issue: Many catch blocks silently return empty lists, null, or do nothing -- swallowing errors that should at minimum be logged. The pattern `} catch (e) { return []; }` appears 10+ times in `lib/services/firebase_service.dart` and 15+ times in `lib/providers/firebase_providers.dart`. Users see empty screens with no indication of what went wrong.
- Files:
  - `lib/services/firebase_service.dart` lines 432-434, 444-446, 504-506, 518-520, 631-633, 738-741, 817-819, 831-834, 898-901
  - `lib/providers/firebase_providers.dart` lines 486, 502, 629, 690, 736
- Impact: Network failures, permission errors, and data corruption silently produce empty UI states. Debugging production issues is nearly impossible.
- Fix approach: Introduce a centralized error reporting utility. At minimum, log all caught exceptions with `debugPrint` (some already do this, be consistent). For user-facing operations, set the provider's `_error` field so the UI can display a retry prompt.

**`_handleAuthException` returns a String but is used as a throw target:**
- Issue: `FirebaseService._handleAuthException()` at line 339 returns a `String`, and callers throw it via `throw _handleAuthException(e)`. Throwing a raw String instead of an Exception breaks `catch (e) { e.toString() }` patterns -- the error message gets wrapped as `"Instance of 'String'"` in some contexts.
- Files: `lib/services/firebase_service.dart` lines 258-260, 285-287, 321-322, 333-334, 339-359
- Impact: Auth error messages displayed to users may show `"Instance of 'String'"` instead of the friendly message. Login/signup catch blocks in `lib/features/auth/login_screen.dart` and `lib/features/auth/signup_screen.dart` call `e.toString()` which prepends "Exception: " or shows the raw String.
- Fix approach: Change `_handleAuthException` to return an `Exception` object: `return Exception(_handleAuthException(e));` at throw sites, or change the method signature to `Exception _handleAuthException(...)`.

**Provider architecture causes unnecessary widget rebuilds:**
- Issue: All three main providers (`RecipeProvider`, `UserProvider`, `GroceryListProvider`) extend `ChangeNotifier` and call `notifyListeners()` for every state change. Screens use `context.watch<RecipeProvider>()` which rebuilds the entire widget tree on any change. - Files: `lib/features/home/home_screen.dart`, `lib/features/search/search_screen.dart`, `lib/features/scan/scan_screen.dart`
- Impact: Performance degradation on lower-end devices. Favoriting a recipe causes the entire home screen grid to rebuild.
- Fix approach: Use `context.select<RecipeProvider, T>()` for fine-grained subscriptions (already mentioned in CLAUDE.md but not practiced). Consider splitting providers into smaller, focused notifiers.

**Grocery list sync has race conditions:**
- Issue: `GroceryListProvider._pushToCloud()` is fire-and-forget (called without await in `addItem`, `toggleItem`, `removeItem`). If multiple rapid toggles occur, the last write may not contain all intermediate changes. Additionally, `_saveLocalItems()` is also not awaited in those methods.
- Files: `lib/providers/firebase_providers.dart` lines 742-751, 778-786
- Impact: Checked/unchecked state can desync between local and cloud. Items may appear to toggle back on app restart.
- Fix approach: Debounce cloud pushes (e.g., 500ms delay), or await the cloud push in a queue to serialize writes.

**Search history grows unbounded in Firestore:**
- Issue: `addSearchHistory()` in `lib/services/firebase_service.dart` (line 874) uses `FieldValue.arrayUnion` to append to the `search_history` array field on the user document. There is no limit on array size. Over time, the user document grows, increasing read costs and latency.
- Files: `lib/services/firebase_service.dart` lines 874-886
- Impact: Firestore documents have a 1MB size limit. Heavy users could eventually hit this limit, causing writes to fail. Read performance degrades as the array grows.
- Fix approach: Trim the array server-side (Cloud Function) or client-side -- keep only the latest N entries. Alternatively, move search history to a subcollection.

**`GroceryList.createdAt` parsed from String, not Timestamp:**
- Issue: `GroceryList.fromJson()` at line 291 in `models.dart` parses `created_at` with `DateTime.tryParse(json['created_at'] ?? '')`. But Firestore stores this as a `Timestamp` (via `FieldValue.serverTimestamp()`). `DateTime.tryParse` on a `Timestamp` object returns null, so `createdAt` always falls back to `DateTime.now()`.
- Files: `lib/models/models.dart` line 291
- Impact: Grocery list ordering by `createdAt` is unreliable since every list appears to be created "now".
- Fix approach: Handle both types: `createdAt: json['created_at'] is Timestamp ? (json['created_at'] as Timestamp).toDate() : DateTime.tryParse(json['created_at']?.toString() ?? '') ?? DateTime.now()`.
