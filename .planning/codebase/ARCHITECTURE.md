# Architecture

> Generated by gsd-codebase-mapper | Focus: arch | Date: 2026-03-24

## Pattern Overview

**Overall:** Feature-first with a Singleton service layer and Provider-based state management.

**Key Characteristics:**
- Feature-first directory layout: each screen lives in `lib/features/{feature_name}/`
- Single `FirebaseService` singleton handles all backend I/O (Firestore, Auth, Vision API, TheMealDB)
- Five `ChangeNotifier` providers manage all application state, registered in `lib/main.dart` via `MultiProvider`
- GoRouter with `ShellRoute` for bottom-nav persistence and auth guard redirect
- Offline-first caching: local JSON fallback, SharedPreferences for grocery/favorites, Firestore offline persistence

## Layers

**Presentation Layer:**
- Purpose: Screens, reusable widgets, navigation shell
- Location: `lib/features/`, `lib/shared/widgets/`
- Contains: StatefulWidget screens, StatelessWidget reusable components, GoRouter configuration
- Depends on: Providers (via `context.read`/`context.watch`), Theme system, Models
- Used by: GoRouter routes in `lib/app/routes.dart`

**State Management Layer (Providers):**
- Purpose: Holds reactive application state, mediates between UI and service
- Location: `lib/providers/`
- Contains: `RecipeProvider`, `UserProvider`, `GroceryListProvider`, `MealPlanProvider`, `NutritionProvider`
- Depends on: `FirebaseService`, `SharedPreferences`, Models
- Used by: All feature screens via `context.read`/`context.watch`/`context.select`

**Service Layer:**
- Purpose: All external I/O -- Firebase Auth, Firestore CRUD, Cloud Vision REST API, TheMealDB HTTP API
- Location: `lib/services/firebase_service.dart`, `lib/services/voice_search_service.dart`
- Contains: Singleton `FirebaseService`, `VoiceSearchService` wrapper
- Depends on: Firebase SDKs, Dio HTTP client, `speech_to_text` package, Models
- Used by: Providers (primary consumer), some screens directly (ScanScreen calls `FirebaseService().analyzeImage()` and `searchByIngredients()` without going through provider)

**Data/Model Layer:**
- Purpose: Immutable data classes with serialization
- Location: `lib/models/models.dart`
- Contains: `Recipe`, `Nutrition`, `AppUser`, `GroceryList`, `GroceryItem`, `DetectedIngredient`, `BoundingBox`, `MealPlan`, `NutritionGoals`, `SearchHistory`
- Depends on: `cloud_firestore` (for `Timestamp`, `DocumentSnapshot`)
- Used by: All layers

**Theme/Design System Layer:**
- Purpose: Colors, typography, spacing constants, Material 3 theme configuration
- Location: `lib/app/theme/`
- Contains: `AppColors`, `AppTypography`, `AppSpacing`, `AppTheme`, `Gap`/`HGap` spacing widgets
- Depends on: `google_fonts`
- Used by: All widgets

**Utilities Layer:**
- Purpose: Pure helper functions with no external dependencies
- Location: `lib/utils/`
- Contains: `IngredientParser` (spoken text to ingredient list), `MealClassifier` (recipe to meal-slot matching)
- Depends on: Models only
- Used by: `ScanScreen`, `PlannerScreen`

**Constants Layer:**
- Purpose: Centralized string constants to avoid magic strings
- Location: `lib/app/constants.dart`, `lib/constants/firestore_constants.dart`
- Contains: `PrefKeys`, `AppUrls`, `AppMeta`, `FirestoreCollections`, `FirestoreFields`, `AppLayout`
- Used by: Providers, services, screens

## Data Flow

**Recipe Loading (Home Screen):**

1. `HomeScreen.initState()` calls `context.read<RecipeProvider>().loadRecipes()`
2. `RecipeProvider.loadRecipes()` Phase 1: calls `FirebaseService().getLocalRecipes()` to load `data/recipes.json` via `rootBundle`
3. Provider sets `_recipes` and calls `notifyListeners()` -- UI renders instantly from local data
4. Phase 2: calls `FirebaseService().getAllRecipes()` which tries Firestore (5s timeout), falls back to local JSON
5. Provider updates `_recipes` with network data if available, calls `notifyListeners()` again
6. UI rebuilds with `context.watch<RecipeProvider>().recipes`

**Ingredient Scan Flow:**

1. User picks image via `ImagePicker` in `ScanScreen`
2. `ScanScreen` calls `FirebaseService().analyzeImage(image)` directly (not through provider)
3. `analyzeImage()` base64-encodes the image, POSTs to Google Cloud Vision REST API with `VISION_API_KEY`
4. Response labels are filtered through `_foodKeywords` allowlist and `_minVisionConfidence` (0.65) threshold
5. Returns `List<DetectedIngredient>` sorted by confidence descending
6. User taps "Find Recipes" -> `FirebaseService().searchByIngredients()` runs local cache matching with tier-based scoring
7. Results displayed as vertical list with match-count badges

**Grocery List Sync (Offline-First):**

1. `GroceryListProvider._init()` loads items from `SharedPreferences` (JSON format), then tries cloud merge
2. Every mutation (`addItem`, `toggleItem`, `removeItem`) immediately updates `_items`, saves to `SharedPreferences`, then pushes to Firestore asynchronously
3. Cloud sync uses a "cloud checked state wins" merge strategy
4. If Firestore is unreachable, local changes are preserved -- non-blocking

**Auth Flow:**

1. `GoRouter.redirect` checks `FirebaseService().isSignedIn` on every navigation
2. Unauthenticated users are redirected to `/get-started` (exception: `/recipe/:id` is publicly accessible)
3. Authenticated users trying to access auth screens are redirected to `/`
4. On login, `UserProvider` loads or creates the Firestore user profile
5. On logout, `FirebaseService.signOut()` signs out from both Firebase Auth and Google Sign-In, then clears recipe cache

**State Management:**
- All five providers extend `ChangeNotifier` and are registered via `MultiProvider` in `lib/main.dart`
- Screens use `context.watch<T>()` for reactive rebuilds, `context.read<T>()` for one-shot method calls
- Each provider holds its own `_isLoading` and `_error` state for independent loading/error tracking
- Favorites are dual-persisted: `SharedPreferences` for offline access, Firestore for cross-device sync

## Key Abstractions

**FirebaseService (Singleton):**
- Purpose: Central data gateway -- all Firestore, Auth, Storage, and external API calls
- Location: `lib/services/firebase_service.dart`
- Pattern: Classic singleton via `factory FirebaseService() => _instance`
- Contains in-memory recipe cache with 30-minute expiration (`_cachedRecipes`, `_cacheTimestamp`)
- Dio HTTP client with retry interceptor (3 retries, exponential backoff) for network resilience

**VoiceSearchService:**
- Purpose: Wraps `speech_to_text` with a clean callback API and 4-state machine
- Location: `lib/services/voice_search_service.dart`
- Pattern: Instantiated per screen, not singleton; stores session callbacks for engine-level error/status handlers

**Models (Immutable Data):**
- Purpose: All domain objects with `const` constructors, `copyWith()`, `fromJson()`/`toJson()`
- Location: `lib/models/models.dart` (single barrel file)
- Pattern: All models in one file, immutable with named parameters
- `Recipe.fromJson()` handles both local JSON format and TheMealDB API format (dual parsing)

**Theme System:**
- Purpose: Material 3 theming with custom brand colors (orange-primary)
- Location: `lib/app/theme/` (barrel export via `theme.dart`)
- Pattern: Static-only classes (`AppColors._()`, `AppSpacing._()`, `AppTheme._()`)
- Provides `Gap`/`HGap` widgets as spacing primitives alongside `AppSpacing` constants

## Entry Points

**App Entry:**
- Location: `lib/main.dart`
- Triggers: App launch
- Responsibilities: Firebase init, `FirebaseService().initialize()`, orientation lock, onboarding check, `MultiProvider` registration, `MaterialApp.router` with GoRouter

**Router Configuration:**
- Location: `lib/app/routes.dart`
- Triggers: All navigation events
- Responsibilities: Auth redirect guard, ShellRoute with bottom nav (Home, Search, Planner, Profile), full-screen routes (Scan, Grocery, Recipe Detail, Meal Plan, Nutrition Goals, Onboarding, Auth screens)

**Firebase Configuration:**
- Location: `lib/firebase_options.dart`
- Triggers: `Firebase.initializeApp()` in `main()`
- Responsibilities: Platform-specific Firebase project config (Android and Web configured; iOS/macOS/Windows are placeholders)

## Error Handling

**Strategy:** Defensive catch-and-continue with local fallbacks. Errors are stored in provider `_error` fields but rarely surfaced to the user beyond SnackBars.

**Patterns:**

- **Service layer:** Methods catch exceptions and return empty results (`return []`) or `null`. The service never throws to the provider except for auth errors.
  ```dart
  // In FirebaseService._getFirestoreRecipes():
  } catch (e) {
    return []; // Silent fallback
  }
  ```

- **Provider layer:** Wraps service calls in try/catch, stores error in `_error`, calls `notifyListeners()`. Some methods rethrow (auth flows) so the screen can display the error.
  ```dart
  } catch (e) {
    _error = e.toString();
    _isLoading = false;
    notifyListeners();
    return [];
  }
  ```

- **Auth errors:** `FirebaseService._handleAuthException()` maps Firebase error codes to user-friendly messages. Auth providers rethrow to let login/signup screens display error text.

- **Vision API errors:** `ScanScreen` catches errors from `analyzeImage()` and shows context-specific SnackBar messages (API key missing vs. general failure).

- **Grocery list sync:** Cloud push failures are silently swallowed (`// Non-critical`). Local state always takes priority.

## Cross-Cutting Concerns

**Logging:** `debugPrint()` for non-critical errors (failed Firebase syncs, auth edge cases). No structured logging framework.

**Validation:** Minimal -- auth screens likely do basic email/password validation in the UI. No centralized validation layer.

**Authentication:** `GoRouter.redirect` in `lib/app/routes.dart` provides route-level auth guard. `FirebaseService().isSignedIn` is the synchronous check. `/recipe/:id` is exempt (publicly accessible for shared links). Auth state flows through `UserProvider` which loads/creates the Firestore user profile after login.

**Caching:**
- Recipe cache: In-memory `List<Recipe>` in `FirebaseService` with 30-minute TTL
- Favorites: `SharedPreferences` key `favorite_ids` + Firestore `favorite_recipes` array
- Grocery items: `SharedPreferences` JSON + Firestore `grocery_lists` collection
- Theme preference: `SharedPreferences` key `dark_mode`
- Nutrition log: `SharedPreferences` key `nutrition_log_YYYY-MM-DD` (daily)
- Firestore: SDK-level offline persistence enabled with unlimited cache size

**Theming:** Light and dark themes defined in `lib/app/theme/app_theme.dart`, toggled via `UserProvider.isDarkMode` and persisted in SharedPreferences. `Consumer<UserProvider>` in `main.dart` rebuilds `MaterialApp.router` on theme change.
